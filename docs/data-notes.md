# Data notes

The demo data is generated by `scripts/generate-seed.ts` from a fixed seed, so every run writes the same files. Person and company names are invented; cities, skills, roles, schools and degrees are ordinary real-world values. Run `node scripts/explore/profile.js` for full counts and `node scripts/explore/consistency.js` to re-check the rules below.

| File | What it holds |
| --- | --- |
| `seed/candidates.json` | 5,000 candidates (top level is a JSON array) |
| `seed/queries.json` | 10 example briefs, each with the filters it should map to and the matching ids |
| `seed/holdout.json` | 40 more briefs in the same format: abbreviations, synonyms, OR-lists, years, companies, schools, degrees, unsupported parts |
| `seed/stripe-events.json` | 5 signed webhook events for acme and globex |
| `public/logos/*.svg` | one logo per company |

`expected_ids` are computed by `matches()` in the generator: plain TypeScript over the generated objects, written separately from the SQL function. `npm run test:sql` checks the SQL against it; `npm run eval` checks the model.

## Candidate shape

| Field | Example | Notes |
| --- | --- | --- |
| `id` | `"cand_0001"` | `cand_` + 4 digits. Sorts correctly as text. |
| `full_name` | `"Wendell Jablonski"` | First + last name from invented lists. Names repeat; ids do not. |
| `avatar_url` | `"data:image/svg+xml,..."` | Inline SVG: initials on a coloured tile. |
| `headline` | `"Junior Machine Learning Engineer · PyTorch, LLMs, CUDA"` | `current_title · ` + 3 of the person's skills |
| `current_title` | `"Junior Machine Learning Engineer"` | Seniority prefix + role |
| `current_company`, `current_company_logo_url` | `"Marbleton Retail"`, `"/logos/marbleton-retail.svg"` | Same as the current experience |
| `role` | `"Machine Learning Engineer"` | 13 role families |
| `seniority` | `"junior"` | `junior` / `mid` / `senior` / `staff` |
| `years_experience` | `1` | 0 to 15, uniform |
| `location` | `{ "city": "San Francisco", "state": "CA", "country": "US" }` | 10 US cities |
| `open_to_work` | `false` | About 30% true |
| `skills` | `["CUDA","Kubernetes","LLMs","PyTorch","SQL"]` | 3 to 6, all from the role's skill set, sorted |
| `experiences` | | 1 to 4, newest first; exactly one current job (`end_year: null`), always first |
| `education` | | Always exactly one entry |

Experience: `title`, `company`, `company_logo_url`, `company_type` (`startup` / `enterprise`, fixed per company), `start_year`, `end_year`, `description` (always `"<title> at <company>, working mostly with <skill> and <skill>."`). Education: `school`, `degree`, `field`, `graduation_year`.

## Rules the generator follows

- **Seniority bands do not overlap:** junior 0–2 years, mid 3–5, senior 6–9, staff 10–15. "senior" and "6 to 9 years" select the same people.
- **Title = prefix + role:** `Junior `, none for mid, `Senior `, `Staff `. There is no Lead, Principal, Director or Head of.
- **A person never changes role family.** Past titles are the same role at the seniority they had when that job started.
- **Work history spans the whole career:** the first job starts in `2026 - years_experience`.
- **Each role has a fixed skill set.** Most skills belong to one role (Swift → Mobile, Go → Backend, Enterprise Sales → Account Executive). Shared ones: React (Frontend, Full Stack), TypeScript (Frontend, Full Stack, Mobile), Python, Kubernetes, SQL, AWS, A/B Testing, User Research.
- **Fields of study follow the role group:** engineers study CS, Computer Engineering, EE or Maths; data scientists CS, Economics, Maths, Physics or Statistics; designers Design, Fine Arts, HCI or Psychology; business roles Business, Communications, Economics, Marketing or Psychology.
- **Companies:** 16 startups and 12 enterprises. The only company attribute is the type; there is no size, stage, funding or industry field.
- No languages, salary, visa, remote/hybrid, age, gender, GPA, certifications or team size anywhere in the data.

## Vocabulary traps

The data is clean (no case or spelling variants), so the mess is all on the brief side. These collisions need care in the prompt:

- **"Austin"** is a city and part of a school (University of Texas at Austin). **"New York"** is a city and part of New York University.
- **"Enterprise"** is a skill (`Enterprise Sales`) and a company type (`enterprise`).
- **"Machine learning"** is a skill (Data Scientists only) and a role (Machine Learning Engineer).
- **"React"** vs **"React Native"**, and **"Swift"** vs **"iOS"**, are different skills.
- **"Product"** spans Product Designer and Product Manager.
- Awkward skill forms: `Postgres` (not PostgreSQL), `Node.js`, `Next.js`, `Go` (not Golang), `CI/CD`, `A/B Testing`, `LLMs`, `dbt`, `gRPC`, `iOS`, `R`. The synonyms in `lib/search/synonyms.ts` map brief wording (k8s, golang, NYC, CMU, master's...) onto these.

## How briefs map to filters

Every constraint in a brief is required (AND). Ranking is years of experience descending, then id.

| Brief wording | Filter |
| --- | --- |
| "senior" / "staff" / "junior" / "mid-level" | exactly that seniority band |
| "5+ years", "3 to 6 years" | `min_years` / `max_years` |
| a role ("backend engineers", "recruiters") | `roles` |
| a technology ("React engineers", "knows Go and Kubernetes") | `skills` (all of them), any role |
| "Vue or Svelte" | `skills_any` |
| "in Boston or Miami" | `cities` (any of them) |
| "worked at a startup" / "at Cobalt Freight" | some job, current or past, matches |
| "currently at ..." | the same, current job only |
| "studied at", "went to" | `schools`; "with a PhD" → `degrees`; "master's" → MS + MBA; "bachelor's" → BS + BA |
| "open to work", "looking for a job" | `open_to_work = true` |
| "engineers" with no role or skill | the seven engineering roles |
| "nice to have X", "bonus if" | ignored (optional) |
| languages, salary, visa, Principal, unknown cities, quality words ("great") | unsupported → zero results with a reason |

## Stripe events

Signed with `whsec_findlark_demo_sample` (HMAC-SHA256 of `${t}.${payload}`). In delivery order:

| # | Event | `created` | Effect |
| --- | --- | --- | --- |
| 1 | acme subscribes (`evt_demo_acme_1`, active) | T | applied → acme paid |
| 2 | the same event again, new header `t` | T | duplicate → ignored |
| 3 | globex update (`evt_demo_globex_2`, active) | T+120 | applied → globex paid |
| 4 | globex create (`evt_demo_globex_1`, incomplete), sent last | T+60 | stale: older than stored → ignored |
| 5 | acme cancels (`evt_demo_acme_2`, deleted, canceled) | T+180 | applied → acme free |

Final plans: acme free, globex paid. In the out-of-order pair the older event has the *later* header `t`, so ordering by the header would get globex wrong; the app orders by `event.created`.
